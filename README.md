# CareerOps

A private HTML/CSS/JavaScript dashboard and Python service for an India SRE/DevOps job search. It reads public Greenhouse, Lever, Ashby and Jobicy feeds, ranks roles using the supplied resume, prepares cover letters/outreach/checklists, and tracks real applications separately from prepared drafts. It never submits applications or sends messages.

## Features

- Search and filter live leads, view source health, review seniority/location evidence, and generate application packets.
- Resume PDF is stored behind authentication in the database, not under public static files or in Git.
- Mark Applied only after confirming an actual employer submission; retain an event history and optional confirmation URL.
- Hourly scheduled scans, configurable from the dashboard. A database lease prevents overlapping scans and catches up overdue scans after a restart.
- `/healthz` and `/health` are public, fast liveness endpoints. `/readyz` checks database availability. Health requests never trigger scans or disclose resume/application data.
- SQLite for local use; external Postgres for Render durability. The service refuses to start on Render without Postgres and authentication.

## Local preview

Use Python 3.10+ (3.12 is used here). Install requirements in a virtual environment, then run `start-local.cmd`. Open http://127.0.0.1:8765. Local preview skips login only for loopback requests and binds only to loopback. It cannot be enabled on Render. It is available while the process runs.

The existing Python on this machine's PATH is 3.6; use `.venv\Scripts\python.exe`, not that older interpreter.

The provided resume was imported into local private storage. On a new cloud deployment, upload it in Profile once; the PDF is deliberately excluded from the repository. The public profile.json is a generic template. A personal matching profile can be seeded through the private INITIAL_PROFILE_JSON environment variable and edited after sign-in. Personal achievements, contact details and resume files are not published in Git.

## Free Render deployment

1. Push the source files to a private GitHub repository, excluding `.venv`, `private`, `data`, exports and secrets.
2. Create a free Neon Postgres project (or use another existing durable Postgres database). Copy its SSL database connection URL into Render's private environment settings.
3. Connect the repository on Render and use the root `render.yaml` Blueprint. The service plan is explicitly `free`. Provide `DATABASE_URL` and a strong `DASHBOARD_PASSWORD`; `SECRET_KEY` and an optional automation bearer token are generated by Render.
4. Deploy, sign in at the resulting URL, upload the supplied resume in Profile, and select Run scan. Verify source results and packets in the dashboard.
5. Put `https://YOUR-SERVICE.onrender.com/healthz` in your UptimeRobot HTTP monitor. `/readyz` can be monitored separately for database readiness.

Render's free service can sleep after 15 minutes of inactivity, restart, suspend at quotas, or experience cold starts. Its filesystem is ephemeral, so SQLite is not supported in hosted mode. Render's free Postgres expires after 30 days; it is not used by this configuration. Neon offers a free tier subject to its quotas. No paid Render cron, persistent disk or worker is provisioned.

Uptime monitoring does not guarantee continuous execution or availability. The scheduler runs while the service process is active; after a pause it catches up once the service wakes and the next scheduler check occurs (within roughly 30 seconds after initialization, subject to cold start). Keep the dashboard's last/next run and source-health states visible. A separate external scheduler can optionally invoke `POST /api/automation/run` with `Authorization: Bearer AUTOMATION_TOKEN`; do not put that token in the browser or health-monitor URL.

## Security and data

All job/profile/resume/export/write APIs require authentication. Writes use a per-session CSRF token. The public login and health endpoints expose no candidate details. Cookies are secure on Render and HTTP-only; the app serves only its own scripts/styles and treats job text as data. The dashboard password and signing key belong in Render environment variables, not source files.

The public job feeds do not provide verified hiring contacts, complete funding history, current salary/notice-period answers or proof of India eligibility. Drafts only use your saved resume facts. Check each role and answer employer-specific questions before submitting on the employer's website. Uploading a different resume invalidates prepared packets; review saved achievements to keep them accurate.

## Schedule

Default: every hour while the hosted process runs. The dashboard supports 1, 3, 6, 12 or 24 hours, pause/resume, and an immediate scan. Due state and run history persist in Postgres. An application is never submitted by the scheduler.

The service uses one Gunicorn worker with threads and overrides Render's default GUNICORN_CMD_ARGS to avoid preloading. This starts the scheduler inside the serving worker rather than before a process fork.

The scheduler checks its saved schedule in memory between runs. Dashboard snapshots are cached for up to an hour and invalidated by writes or scan completion; CSRF tokens remain session-specific. Resume checks read metadata instead of downloading the PDF, and single-job actions query one job. These choices let Neon sleep between scans and reduce database transfer. The active-catalog/tracked-job list should gain pagination before expanding to a large catalogue or long application history; current matching still processes that list on the server. Counts reuse the rows needed for the dashboard, and the queries do not duplicate wide job records through joins.

## Checks

Run `.venv\Scripts\python.exe -m unittest -v` for the behavior/API tests. A real source scan is a separate integration check. The source catalogue has 18 verified employer boards plus two keyword feeds from Jobicy (20 endpoints). Recent funding is not assumed. Only relevant role/location records are persisted; the run total reports all screened openings.

## Fresh discovery and progress badges

The default discovery view requires a source publication timestamp within the rolling last 24 hours, an India/possibly India-eligible location, DevOps/SRE title, no senior title and a parsed minimum experience requirement of at most two years. This is a review aid, not proof of eligibility. A missing experience requirement stays in review. Lever creation timestamps are not treated as publication dates. First-seen and last-seen never make an old opening fresh. The cutoff is re-evaluated even when the database snapshot is cached.

Jobs are grouped by publication day in Asia/Kolkata; a rolling 24-hour window may cross two calendar dates. Alert receipt dates have their own labelled groups. The Applications view keeps older saved history. Pending badges count only unsubmitted, verified last-24-hour entry / two-year roles with source-reported fewer than 25 applicants. Older saved packs are retained in application history. Submitted badges require an explicit owner confirmation or an unambiguous portal confirmation email, and remain submitted as the pipeline progresses to interviews.

Exact application destinations are deduplicated after removing tracking parameters while retaining requisition parameters. A portal copy can also merge with one unambiguous employer record with the same company, title and location. Distinct employer requisition IDs and ambiguous matches remain separate. This avoids silent false merges; different spellings or locations can still need manual review. Original source keys and submission history are retained.

## Free portal email bridge

LinkedIn, Naukri, Foundit, Indeed, Glassdoor, Instahyre, Cutshort, Wellfound, TimesJobs and Hirist have alert adapters. These are email imports, not direct portal crawlers. Enable matching free alerts on the portals you use. In Automation, download the authenticated private Apps Script, paste it into a Google Apps Script project, run `installCareerOpsHourly`, and approve Google access. Google then runs it every hour independently of your computer. The script reads matching last-three-day alert threads and posts their vacancy cards to this dashboard; it never sends email or submits applications. Google time triggers are approximate, not an exact wall-clock SLA. The script checks up to 100 matching threads per execution and sends small batches.

`GmailApp` requests Gmail access at Google's consent screen; review that permission before approving. The import token is derived from the workspace signing secret and restricted to `/api/alerts/ingest`. Keep the personalized download private; it is not committed. Rotating SECRET_KEY invalidates it. Import requests are bearer protected and have a 5 MB request limit. The stored record contains the job card and clean job URL, not the whole mailbox message or personalized tracking tokens. Unsupported email templates / redirect-only links are skipped; source coverage is not guaranteed for every portal.

Posting dates often are absent in alert emails. Those records display receipt time and require date/experience review; receipt time never qualifies them for the strict fresh-posting queue. The dashboard shows setup needed until the cloud bridge has actually contacted it. A one-time connector import does not claim that hourly sync is installed. See [LinkedIn automation limits](https://www.linkedin.com/help/linkedin/answer/a1341387/prohibited-software-and-extensions), [Naukri free alerts](https://resume.naukri.com/frequently-asked-questions-faq/how-to-create-free-job-alerts/), [Jobicy API](https://github.com/Jobicy/remote-jobs-api) and [Google time triggers](https://developers.google.com/apps-script/guides/triggers/installable).

## Strict latest-job filter and submission reconciliation

Default discovery requires a source posting time within 24 hours, an entry / at-most-two-year DevOps/SRE requirement, and source-reported applicant evidence below 25 observed within the last hour. A count of exactly 25 fails. Missing counts are unknown, never zero. Exact counts and explicit upper-bound badges remain distinct; counts can change after observation. Relative posting times use their oldest possible rounded time, and descriptions with an explicit old original publication date cannot become fresh via reposting. Unknown dates are excluded even if an alert arrived today. The optional unknown-count view still requires a verified posting within 24 hours.

The existing free feeds and many portal emails do not publish applicant counts or original posting times. Such jobs cannot be verified for the strict list; no complete free live applicant-count API is configured. A native LinkedIn search shortcut is provided with filters actually checked in the signed-in UI: India, Past 24 hours, Entry-level, Under 10 applicants (a stricter subset of under 25). LinkedIn can also return related suggestions or older reposts; its page must be reviewed for actual experience and original dates.

The hourly Gmail bridge also searches explicit application confirmation subjects. Strong LinkedIn confirmations match the exact original job URL, before any recommended-jobs section. Supported Naukri summaries match only a visible confirmed card against one unambiguous saved company/title; subject totals are not converted into invented applications. Receipts remain private, reconciliation is idempotent, and reimporting a vacancy does not reopen its application. Interview and later stages are preserved. A one-click 'Maine submit kar diya' action records an explicit owner confirmation immediately. Opening an external Apply link never counts as submission.
